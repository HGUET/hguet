# B-012 analysis: unchecked `Transfer` under signed mint caps

**Question.** Scenario B-012 (label BAD, HGUET answers DENY) contains a top-level SPL Token opcode 3
`Transfer` while the verified intent carries signed per-mint caps. Is that a *proven violation of the
signed scope* (DENY) or *insufficient coverage* (UNKNOWN)?

## Facts

* Opcode 3 `Transfer` encodes source, destination, authority and an amount. It does **not** name the
  mint and carries no decimals check. Offline, the mint of the source account is unknown.
* Signed caps are per mint (`token_spend_limits`) or per source (`token_source_limits`).
* The documented contract (`docs/implementation/README.md`, "signed mint caps") defines the validator as
  summing "only these top-level original wire instructions **with an explicitly named mint**": checked
  transfer, checked burn, Token-2022 fee transfer. It states that an unchecked `Transfer` "makes
  signed-intent validation fail closed ... intentionally restrictive".
* The `limitation` string emitted by the CLI says the same: "Signed caps reject uncovered direct Token
  Program instructions".

## Two defensible readings

| Reading | Argument | Consequence |
|---------|----------|-------------|
| **Coverage gap (UNKNOWN)** | The tool cannot compute the spend against any cap because the mint is unknown; nothing proves the cap is exceeded or that a forbidden mint is touched. Legitimate wallets do emit opcode 3. | DENY would claim knowledge the tool lacks |
| **Form violation (DENY)** | A capped intent authorises debits only in a form that names the mint. An instruction that cannot be bound to a cap is, by the signed contract, *not an authorised debit*. | DENY is a statement about the signed form, not about a proven loss |

## Determination

**B-012 is a proven violation of the signed scope's FORM, not a proven over-cap spend. DENY stands, and the
label BAD stands**, for these reasons:

1. The contract is explicit and was signed into the intent's meaning: with caps present, only mint-named
   checked debits are authorised. Whether opcode 3 *happens* to be within a cap is irrelevant, because
   the issuer's authorisation cannot cover an unbound debit.
2. The distinction that separates it from the HG-BENCH-002 cases is **what is missing**. Unresolved ALT or
   multisig accounts are missing *evidence about a form the contract allows*. An unchecked `Transfer` is a
   form the contract does **not** allow. The former is UNKNOWN, the latter DENY.
3. The cost of the alternative reading is a gap: an attacker could always use opcode 3 to evade every cap.
4. Residual cost of this reading: a legitimate dApp that emits opcode 3 is blocked **only when the issuer
   chose caps**; the issuer can re-issue the intent in checked form or without caps (then UNKNOWN).

The determination is deliberately narrow:

| Case | Result | Pinned by |
|------|--------|-----------|
| unchecked `Transfer` **with** token caps | DENY (form violation) | B-012, B-112 |
| same payment as `TransferChecked` within the cap | not DENY | G-104 |
| unchecked `Transfer` under a **SOL-only** intent (no token scope to violate) | UNKNOWN + `SIGNED_INTENT_TOKEN_CAP_UNSPECIFIED` | U-110 |
| administrative / unsupported opcodes under caps | UNKNOWN (coverage gap) | G-102, G-103, U-108, U-109 |

## What was NOT changed

B-012's label and rationale in the original 60 scenarios are untouched. The regression pairs B-112 /
G-104 / U-110 were added instead. HGUET's behaviour did not change; the new tests pin the boundary so a
future change cannot move it silently.

## Open item for the product owner

The finding is reported as the generic `INTENT_REJECTED`. A dedicated code such as
`INTENT_SCOPE_UNBOUND_TOKEN_DEBIT` with `evidence_refs` would make the *form* nature explicit to users.
It is a vocabulary change, not a semantics change, and is left for a separate decision.

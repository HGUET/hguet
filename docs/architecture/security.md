# HGUET CLI — Security architecture and threat model

**Design status:** pre-alpha proposal. This document defines assumptions and failure boundaries, **not audited security claims**.

## 1. Security goal

Protect the decision **before** an AI agent's prospective Solana payment is signed or submitted. The security engine must identify:

- A transaction that differs from a **separately trusted** payment authorization.
- A policy violation, unexpected asset movement or unauthorized authority change.
- Unsupported/opaque instructions, stale or inconsistent RPC evidence, malicious or mismatched x402/MPP payment terms.
- An anomalous payment pattern when reliable history is available.
- Cases where data is insufficient to decide safely.

The engine is **an advisor**. Strong enforcement is a property of the client-controlled signing environment, not of a command printing “DENY”.

## 2. Assets and adversaries

| Asset | Attack objective |
| --- | --- |
| Customer's funds | induce unauthorized or excessive transfer |
| Payment intent | forge or rewrite recipient, amount or authorized task |
| Unspent budget | split purchases or race checks to overspend |
| Transaction representation | conceal dangerous CPI, ALT, extension or fee |
| HGUET Cloud credentials | steal paid checks, access another tenant |
| Security result | forge ALLOW, replay an old ALLOW or change checked bytes |
| Network observations | poison RPC data, induce stale/false “safe” result |
| Local config | add attacker key or downgrade policy / transport |
| Machine telemetry | exfiltrate sensitive transaction or customer data |

Adversaries include: prompt-injection content; compromised AI agent processes; malicious x402/MPP resource providers; malicious/compromised onchain programs; adversarial RPC endpoints; stolen device credentials; compromised Cloud telemetry feed; compromised CI/dependency delivery.

**Out of scope for the standalone CLI:** a fully compromised OS/root account, a signer which does not verify HGUET policy, a customer deliberately overriding denial, Solana consensus failure or future unknowable protocol behavior.

## 3. Trust boundaries

```text
TRUSTED: independent business approver / wallet owner
          |                                  UNTRUSTED: external email,
          |                                  websites, LLM output, RPC data,
          v                                  merchant payment requests
 signed/pinned PaymentIntent                 |
          |                                  |
          +------------+---------------------+
                       v
               HGUET local process
               - untrusted bytes parser
               - deterministic policy
               - evidence reconciliation
                       |
            +----------+------------------+
            |                             |
   user-controlled Solana RPC     explicitly opted-in Cloud
            |                             |
      untrusted state data        authenticated PQ TLS boundary
            |                             |
            +-----------+-----------------+
                        v
                   advisory verdict
                        |
                        v
                separate wallet signer
                (enforcement must be explicit)
```

Trust data according to provenance, not according to attractive formatting or a model's confidence.

## 4. Trusted PaymentIntent (critical differentiator)

An authorized payment intent is **not** simply an arbitrary `intent.json` generated by the agent being examined.

### Intent contents (proposal)

- `schema_version`; `intent_id` random identifier; `purpose` human-readable description.
- `network`/genesis binding; `allowed_fee_payer` or signer constraints.
- `agent_id` and `tenant_id` scopes where independently known.
- `recipient`, `asset_mint`, `token_program`; amount in **integer base units**.
- `max_amount` or `exact_amount`, optional cumulative budget reference.
- `allowed_program_ids` and `denied_operation_classes`.
- `resource_id`, `merchant_origin`, `challenge_digest` for x402/MPP when applicable.
- `issued_at`, `not_before`, `expires_at`; replay reference and optional approved session.
- `issuer_key_id` and a detached signature over a domain-separated canonical encoding.

### Verification

1. Require the trust anchor to have been configured **outside** agent control (OS-protected keyring, admin-managed config, signer integration).
2. Verify signature using established maintained cryptography. Solana-compatible Ed25519 is a candidate for short-lived intents, but **do not conflate that with the mandatory post-quantum Cloud transport**. Future separately standardized signature suites can be versioned.
3. Canonicalize consistently (e.g. RFC 8785 JSON Canonicalization Scheme after strict field/type/schema validation) or use a fixed binary canonical schema; never reserialize differently in signer and verifier.
4. Domain-separate: `HGUET-INTENT/v1` and bind network, issuer, intended agent and expiry.
5. Reject unknown critical fields, duplicate keys, malformed Unicode, invalid base-unit amounts, expiry and replay.
6. Recompute from actual decoded transaction effects; do not compare merely friendly address/token labels.
7. Treat an intent created by the untrusted agent with no verified issuer as **unverified input**. Strict profile → UNKNOWN/DENY based on independently known policy.

A human can deliberately approve a payment via their own protected signer/integration. HGUET does not hold that key.

## 5. Hard policy examples

- Token mint and token program must match approved identities. Symbols and logos are not identity.
- Recipient token account must resolve to expected owner and mint where applicable.
- Total SOL and token debit including fees/rent/extensions must remain in bounds.
- Restrict program IDs, upgrades, authority changes, new delegates and writable accounts.
- Reject unintended CPI side effects and hidden/uninterpretable transfers in strict mode.
- Refuse program updates or newly triggered token-extension behavior when required coverage is missing.
- Bind payment request to price, resource, network, scheme and merchant origin for x402 V2 / MPP.

No “score > threshold” can override a definitive hard deny.

## 6. Spending history and race safety

A free CLI with no privileged signer and no synchronized cross-device state **cannot guarantee a global budget**. The honest free feature is an **advisory local accounting view**.

For optional local state:

- Use SQLite or another transactional, lockable store, with atomic reservations keyed by deterministic payment-intent ID and transaction fingerprint.
- Record `reserved`, `observed_confirmed`, `expired`, `cancelled`, reconciling onchain state only when evidence is known.
- Distinguish **attempted**, **authorized**, **submitted** and **confirmed**; a simulation itself is **not** expenditure.
- Parallel processes must not double-count or double-consume the same reservation; test SQLite transaction isolation.
- Offline/unsynchronized/evicted/migrated state or another agent/device: reduce coverage or UNKNOWN if cumulative budget is mandatory.
- Independent signer enforcement or server-side authoritative accounting is required for hard distributed limits; even Cloud observations alone do not stop payment outside a controlled signer.

## 7. x402 V2 and MPP guard rails

**x402 V2**: inspect the actual payment requirement, selected scheme, CAIP-2 network, asset mint, atomic amount, `payTo` recipient, resource binding, expiry and replay state. A hostile resource can return a legitimate-looking HTTP 402 asking for the wrong recipient. The authorization must come from independent policies or a trusted commercial workflow. Do not accept v1 legacy headers as valid v2 objects.

**MPP**: inspect challenge realm, nonce/expiry, intended resource, charge/session type, SOL/SPL asset and recipient, and receipt provenance; for metered sessions track cumulative vouchers and settlement bounds. MPP specs are evolving internet drafts, so feature support must be explicitly version-locked.

Both integrations must use maintained reference clients/parsers where practical. HGUET **analyzes** payment requests; it does not facilitate settlement. Any optional receipt inspection is passive.

## 8. Privacy and local execution

- `local` means zero HGUET Cloud requests. A user's selected RPC **may receive their unsigned transaction**, including sensitive account relationships; disclose it.
- `inspect --offline` has zero network traffic and only performs format/introspection checks.
- Cloud mode is opt-in for each check/profile, shows the minimum submission payload; default to hashes, read-only features and provenance when full raw transaction is not required.
- No keypair or secret seed input. Secret CLI account keys must live in OS key storage.
- Redact RPC bearer keys, merchant identifiers, account addresses where requested, email and customer documents from logs and crashes. Raw transaction recording is **off** by default.
- Explicit configurable retention on Cloud; no unannounced training/third-party transfer.
- Threat feed ingestion validates schema, origin, expiration and retractions; never interpret unauthenticated feed output as protocol truth.

## 9. Threat-to-mitigation matrix

| Threat | Mitigation | Residual risk |
| --- | --- | --- |
| Prompt injection changes payment instructions | independent signed/pinned intent, deterministic check | malicious human may approve wrong intent |
| Alternate agent execution route | signer integration must require matching verdict | CLI alone cannot prevent bypass |
| Fake token or recipient | compare verified mint, token program, owner and account relationships | unsupported token extensions |
| Cross-program transfer | decode CPI and simulation state/effects; UNKNOWN if opaque | unknown protocol semantics |
| Stale/out-of-date RPC | compare slot/finality, require freshness | live state can still change |
| Transaction changed after review | message hash, intent hash, expiry, signer recheck | ordering/TOCTOU at execution |
| Duplicate/fragmented payments | idempotency, history, atomic reservations | global budget requires signer/server enforcement |
| Fake “SAFE” result | canonical schema, signed Cloud report and pinned signer trust | host can still be compromised |
| Cloud stolen device credential | OS secure storage, rotation, revocation, per-device quota | compromised endpoint can spend credits |
| PQ downgrade | strict TLS group/sig negotiation with fail closed | crypto implementation bugs / future cryptanalysis |
| Payment intelligence false positive | source provenance, explainability, appeals and correction | incomplete intelligence remains |

## 10. Abuse and resilience

Use file/JSON parser fuzzing, bounded CPU and memory, RPC deadlines, modest concurrency, log truncation, strict payload caps, per-device rate limiting (Cloud), no shell execution of external payment content, and outbound target allowlists for automatic integrations.

**Never implement a bespoke cryptographic algorithm**; use maintained audited library bindings, test on each target OS, pin dependencies and record known CVEs.

## 11. Enforcement integration (future optional)

A safe integration looks like:

```text
Agent requests payment
   → customer-controlled signer receives exact unsigned message
   → signer asks HGUET to analyze this same message
   → signer verifies strict verdict, intent hash, issue time & network
   → signer rechecks policy and signs exactly the analyzed message
```

Even a Cloud-signed report confirms **who issued the report and which bytes it covers**; it does not independently prove correctness of all findings. The signer must check authenticity *and* its own trust/policy constraints.

## 12. Review checklist

- No claimant of “guaranteed safe” in CLI help, docs or examples.
- Identity source and payment intent independent of untrusted agent.
- Every known program instruction, CPI and token extension accounted for or marked unknown.
- Simulation mode and original message differences surfaced.
- No Cloud when local; Cloud mode explicit, no TLS downgrade.
- Budget and replay limitations visible.
- Attack fixtures cover all threat categories.
- Independent security assessment before mainnet business use.
